## Межі моделі

**Назва документа:** «довідка про обставини травми (додаток 5 до Наказу №402)». Не скорочуємо її до «Ф5» / «Форми 5». Складає начальник медичної служби, підписує командир частини; форма містить реквізит «Підстава: наказ командира», а крок «рапорт → наказ» у моделі згорнуто. Повний ланцюг «поранення → «Форма 001» → рапорт → наказ → довідка» описано в [AS IS](03-as-is.md#повний-алгоритм-довідки-уточнення-2026-11-14) (рішення команди 2026-11-14: «без TO BE»). За ст.260 п’ятиденний строк охоплює складання і направлення у визначеному випадку дій противника; факт отримання адресатом фіксується окремо. [Правило підтвердженого строку та орієнтира](architecture/adr/0006-primary-trigger-and-certificate-clock.md).

Це **запропонований невиконуваний наскрізний процес**, а не опис запущеної системи чи універсальна процедура для кожного поранення. Один pool об’єднує навчальний сценарій координації; доріжки групують роботу, **не створюють єдиного органу влади чи підпорядкування лікарень, ВЛК та органу призначення ОГД**. У деталях людська дія має префікс виконавця; де суб’єкт залежить від випадку або не встановлений із наявних джерел (`VLK_Send`, `Cert_Send`, `Intake_Review`, `Task_ServiceExecution`), лишено «належний / уповноважений» — це прогалина, а не визначена роль. Військовослужбовець у цій моделі не є обов’язковим виконавцем жодного кроку: його звернення показане лише через `Control_Support`, а дії в застосунку (перегляд стану, підтвердження) окремими вузлами не змодельовані [питання команді, аудит 2026-11-14]. Sequence flow — порядок у цій концептуальній моделі, а не API / передача медичних даних між організаціями. Міжорганізаційні договори й конкретні message flow реальних інтеграцій ще не встановлені.

Згорнутий підпроцес — окрема DI-площина. `receiveTask` означає очікування належного підтвердження, а не припущення про webhook. `serviceTask` — ціль автоматизації: його виконує серверна частина сервісу «Кейс поранення» (оркестратор подій, інтерфейси якого — кабінет бійця й режим командира в Армія+, [концепція, §4](04-feature-concept.md)); МІС ЗСУ, СЕДО й фінансове джерело — зовнішні системи-джерела подій. У затвердженому [прототипі 8б](prototype-8b.md) є локальні handlers і синтетичні джерела; реальних інтеграцій немає. Основний вхід — автентична погоджена подія еПМК з МІС ЗСУ. Адміністративний запит належного командира / супроводу — лише запасний шлях, коли еПМК або її подія недоступна; не рівнозначний основний тригер. Подієвий шлюз приймає основний сигнал або належно обраний резерв; перший прийнятий вхід скасовує альтернативне очікування. Пріоритет еПМК над резервом у графі не виражено умовою — це організаційне правило ADR 0006; відхилення неавторизованого запиту й випадок «збіг спростовано» показані лише приміткою, без окремого вузла [питання команді, аудит 2026-11-14]. Повторні / пізні сигнали йдуть у той самий кейс через перевірений шлюз, не запускають комплект задач знову. Неавторизований запит відхиляється до успішного маршруту.

Після завершення показаного проходу наступне звернення / подія потребує нового проходу координації за тим самим контролем; подієвий підпроцес працює лише поки активний батьківський процес. Це не модель безстрокового фонового воркера.

Клінічна гілка не чекає входу в Армія+, інтернету чи еПМК в сервісі. Адміністративний кейс може існувати без підтвердженого медичного факту. Медичні системи залишаються місцем вводу; нової форми клінічного запису в нашому продукті немає. Для відсутньої події / непогодженого адаптера залишається чинний дозволений документний маршрут і задача уточнення.

Кінець гілки означає завершення **цього проходу / обраного обсягу**, а не автоматичне закриття `WoundCase`, всіх періодів виплат чи задач. Стан «невідомо» у фінансових гілках очікує джерела; часткове виконання повертає в очікування решти. Обидві фінансові площини мають спільний граф і різні підписи; для ОГД — одноразової виплати — «часткове виконання» успадковане від цього графа й є спрощенням моделі [питання команді, аудит 2026-11-14]. Уточнення 2026-11-14: команда вирішила, що ОГД — одна одноразова виплата без часткового виконання ([ADR 0013](architecture/adr/0013-ogd-single-payment-and-facility-referral.md)); граф площини не змінено, тож гілку часткового виконання для ОГД читаємо як невідповідність моделі рішенню. Обґрунтована відмова завершує цей розгляд, але не скасовує право на оскарження. ОГД у моделі стартує лише після чинної постанови ВЛК (`OGD_VLKDecision`): постанова про причинний зв’язок входить до пакета за N07, а продукт не приймає пакет ОГД до неї ([ADR 0011](architecture/adr/0011-payments-after-vlk.md)); останнє — продуктове правило, обережніше за норму. Вирішено 2026-11-14, [журнал рішень](decisions.md).

## Трасування до всього прийнятого обсягу

| F / AC | BPMN / умова поза вузлами |
|---|---|
| F01 / AC01 | `Sub_Intake`, `Gateway_NewCase`, `Control_Repeat`: підтвердження випадку, ручний розбір, повтор без дублювання |
| F02 / AC02 | `Control_Project`, `Control_Review`: джерело / час / свіжість / наступна задача; невідома подія лишається невідомою |
| F03 / AC03 | `Cert_*`, `VLK_Checklist`, `OGD_Checklist`, `Reward_Checklist`: окремі маршрути / правила, refs / отримання / виправлена версія |
| F04 / AC04 | `Cert_Anchor`, `Cert_AnchorKnown` / `Cert_Clarify`, обидва `Timer_*`, `Care_Transfer`: відомі календарні якорі, ручний контроль; сервіс рішень не ухвалює |
| F05 / AC05 | `VLK_Trigger` → `VLK_Referral` → `VLK_Receipt` → `VLK_Decision` → `Task_ServiceExecution`: різні факти й належні виконавці |
| F06 / AC06 | `Sub_Reward` / `Sub_OGD` (після `OGD_VLKDecision`): різні правові підстави, періоди / пакети, причина / повернення / відмова / виконання |
| F07 / AC07 | `Control_Support`, адміністративна ініціація, чинний резерв; загальний гайд без доступу сторонньому; уточнення обліку без створення / скасування СЗЧ |
| F08 / AC08 | `Control_Aggregate`: визначення BO / когорт у фазі 5 й моделі даних; малі та доповнювальні групи приховуються; пороги уточнює фаза 7 |
| F09 / AC09 | Налагоджувальна панель не є посадовим учасником. У прототипі подає лише синтетичні S1–S8 через той самий шлюз у `Sub_Intake` / `EventSub_Control`, з повторами, прогалинами й конфліктами |
| F10 / AC10 | Кожна дія / читання: серверна роль + чинний scope + дозволені поля; джерельний доступ перевіряється повторно. Чотири панелі, заборона клінічних даних командиру, неперсональні агрегати, аудит без PHI, чесний стан мережі й навчальний банер — наскрізні умови, не нові медичні кроки |

Наявність вузла не доводить виконання AC кодом. [P0–P4 / D1 і лінія відсікання](architecture/demo-plan.md) залишаються прийнятими: спершу основа й усі чотири панелі для 8а, потім наскрізний шлях та винятки, потім подача. При нестачі часу скорочуємо косметику / графіки / форми; F / AC й захист не вилучаємо мовчки. Фактичне покриття AC кодом — у [трасуванні](final-traceability.md) та [README прототипу](../prototype/README.md).
