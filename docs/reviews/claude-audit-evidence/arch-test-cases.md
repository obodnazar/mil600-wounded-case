## 2. Тест-кейси, яких бракує (given / when / then)

Усі твердження — через HTTP від імені ролі (не через внутрішній Store).

### Інший порядок подій
- **TC-01 ⚠️ (F002)** Given primary, certificate-prepared. When `certificate-received` (ВЛК) приходить ДО команди й `certificate-issued`, потім issue_certificate, issued, sent, і та сама `certificate-received` доставляється повторно. Then квитанція ВЛК застосована рівно один раз; відповідь на повтор не `duplicate` для ще не застосованої події; відкритих review немає; freshness=fresh.
- **TC-02 ⚠️ (F002)** Given reward-packet ще не надійшов. When `reward-approved` приходить першим, потім `reward-packet`, потім повтор `reward-approved`. Then трек reward=approved; жодного вічного review.
- **TC-03 ⚠️ (F005)** Given primary v1 і v2. When квитанція бійця для v2 (12.11) приходить раніше за квитанцію v1 (10.11). Then якір = правило, погоджене командою (найраніше підтверджене отримання → due 15.11), незалежно від порядку доставки.
- **TC-04 ⬜** Given vlk-received. When `vlk-decision` приходить до `vlk-received` (переставлено), потім пакет. Then постанова застосовується після появи пакета без ручного втручання або має закривний розбір.
- **TC-05 (властивість)** Для кожного ланцюжка (prepared→issued→sent→received; packet→decision→execution; packet→approved→partial→confirmed) усі перестановки доставки дають ту саму кінцеву проєкцію або явний розв’язний розбір; ніколи — мовчазну втрату.

### Повтор після конфлікту
- **TC-06 ⚠️ (F007)** Given прийнята primary. When та сама подія зі зміненим змістом доставляється тричі. Then рівно один відкритий розбір event_conflict; три відповіді 409; аудит не росте лінійно як «denied».
- **TC-07 ⚠️ (F002/F007)** Given розбір event_conflict. When уповноважена роль закриває його рішенням «оригінал чинний». Then freshness повертається до fresh; закриття в аудиті; повторний конфліктний запит знову дає 409 і новий розбір.
- **TC-08 ⬜** Given конфлікт за другим ключем (новий event_id, та сама ревізія stream, інший зміст). Then 409 і розбір прив’язаний до оригінального кейсу.

### Кілька версій поспіль
- **TC-09 ⬜** Given довідка v1 видана й отримана ВЛК. When corrected v2 (supersedes v1), потім corrected v3 із supersedes v1 (застарілий попередник). Then v3 → розбір; чинна v2 без квитанції.
- **TC-10 ⬜** Given пакет ВЛК v1→returned→v2. When v3 із supersedes_revision=v1. Then розбір packet_revision_order_unknown; ревізія лишається v2.
- **TC-11 ⚠️ (F001)** Given primary (enemy_action=yes) + підтверджена квитанція (due 15.11). When еПМК v2 з enemy_action=unknown. Then due лишається 15.11; створено розбір/задачу застосовності; 'unknown' не знижує підтверджене.
- **TC-12 ⚠️ (F001)** Given те саме. When довідка про перебування з enemy_action=no + доказ. Then строк не стирається мовчки: розбір applicability_conflict, обидва джерела видимі належній ролі.
- **TC-13 ⚠️ (F005)** Given primary (внесено 09.11). When та сама еПМК в іншому stream із recorded_at 12.11. Then орієнтир не зсувається без явного виправлення версії.
- **TC-14 ⚠️ (F004)** Given команда issue_certificate, issued v1, withdrawn v1, prepared v3. When `document.issued` v3 без нової команди. Then розбір issue_needs_command (одна команда — одне підтвердження).
