# Концепція функціоналу: «Кейс поранення» в Армія+

> Основа ідеї команди для кроку II (TO BE). Правова ревізія **2026-11-13** затверджена як **варіант А [ADR 0001](architecture/adr/0001-legal-boundaries.md)**. [Фаза 5 — продуктова концепція](05-product-concept.md) деталізує цінність, сценарії, MVP / беклог, критерії й трасування; її обсяг F01–F10 / AC01–AC10 і чотири панелі затверджені Назаром 2026-11-13. [Архітектура фази 6](architecture/README.md) деталізує цю основу й затверджена Назаром 2026-11-13 (варіант А). [TO BE BPMN](06-to-be.md) винесено з фази 9 вперед для кроку II; зараз на затвердженні. Підстави й редакції — [N01–N21](../regulation/README.md), статуси функцій — [L01–L21](../regulation/legality-matrix.md). Позначка **[перевірити]** означає невстановлені технічні права, охоплення або регламент; жодна стрілка нижче не означає готовий production-доступ.

## 1. Що вирішила команда

1. Функціонал робимо як **фічу в Армія+**.
2. Вона **веде військового після поранення** і **перевіряє, чи є всі документи**.
3. **Командир / супровід бачить необхідні службові відомості про лікування своєї частини** за належними повноваженнями; клінічний пакет йому не відкривається.
4. **Тригер** — автентична подія внесення еПМК у МІС ЗСУ після погодження обміну. Паперовий резерв і відсутня подія потребують адміністративного запасного маршруту, а не створення медичного запису командиром.

За затвердженим рішенням фази 2 головна проблема — **гіпотеза непрозорого шляху від медичних документів до обґрунтованого рішення та його виконання**. Болі 1–4 — [карта](../research/pain-map.md); C6 (медична оцінка) поза продуктом, C2 (повернення пакета) — підгіпотеза для опитування й інтерв’ю. Це не доводить масовість чи головний внесок затримки частини.

## 2. Ключовий принцип: Армія+ — вітрина, а не джерело даних

У лекції 2 є думка: «Якщо оцифрувати хаос — буде оцифрований хаос». Якщо боєць фотографує папери і вантажить їх в Армія+, змінюється лише носій, а процес лишається той самий. Тому:

- **Лікарі не отримують нового застосунку.** Ціль — використати їхні чинні системи: МІС ЗСУ / фактичний медичний інтерфейс та МІС цивільного закладу. Типи записів, охоплення й дозволений канал ЕСОЗ / СЕДО перевіряються з власниками.
- **Документ живе в системі, яка його створила.** Наш сервіс зберігає *посилання і статус*, а не копії медичних документів.
- **Завантаження фото — запасний шлях**, із захищеною обробкою та перевіркою уповноваженою особою. Паперова ПМК можлива й зараз за технічного винятку N04; фото не стає підписаним електронним оригіналом.
- **Мета TO BE: боєць нічого не носить.** ВЛК бачить пакет у МІС ЗСУ сама.

## 4. Як це з'єднано з Армія+ (архітектура верхнього рівня)

```
 Джерела (вже існують)                Новий сервіс                      Інтерфейси
 ────────────────────                ──────────────                    ──────────
 MedEvac / МІС ЗСУ  ── еПМК ──┐
 МІС ЗСУ (госпіталі, ВЛК) ────┤      ┌──────────────────────┐   ┌─> Армія+ : кабінет бійця
 Узгоджений цивільний канал* ─┼────► │  «Кейс поранення»    │───┤
 СЕДО (наказ, дод. 5) ────────┤      │  оркестратор подій   │   ├─> Армія+ : режим командира /
 Фінслужба (виплати) ─────────┤      │  + чекліст + строки  │   │   служби супроводу
 Імпульс / ДРВ (хто, де служить)┘    └──────────────────────┘   └─> МІС ЗСУ : кабінет ВЛК (пакет)
```

\* Цільова інтеграція: СЕДО за №901 або окремо погоджений доступ МІС / ЕСОЗ. №4497-IX не дозволяє будь-який експорт епікризів. Технічні протоколи, обсяг і права нового сервісу не отримані.

- **«Кейс поранення»** — бекенд-сервіс у контурі МОУ. Логічно зробити його частиною ІКС «Супровід», яку зараз розробляють, а не дублювати [перевірити з ГУІТ].
- Цільово він **отримує погоджені події** з джерел: еПМК, переміщення / виписка, довідка, постанова ВЛК та окремі фінансові етапи. Наявність і семантика кожної події потребують підтвердження власника.
- За погодженими правилами він **підказує** потрібні документи для конкретного маршруту й контролює строки: чотири календарні місяці від початку лікування для відповідного огляду; п’ять днів на довідку у випадку дій противника від визначеної в ст.260 Статуту події. Якщо дата не підтверджена, строк не вигадується (N05, N16).
- Армія+ — цільова вітрина для бійця й належних службових ролей. Її довірена сесія / mapping новому сервісу ще потребує контракту власника. Army ID, MIL ID і номер військового документа різні; [ADR 0005](architecture/adr/0005-identity-and-case-linking.md) пропонує окреме зіставлення особи, випадку та службового scope.

### Яка база даних потрібна

Початковий ескіз метаданих наведено нижче; актуальна логічна [модель фази 6](architecture/data-model.md) додає правила, квитанції, області доступу й транзакційні гарантії. Вона ще очікує затвердження, фізичної БД немає:

| Сутність | Поля (приклад) |
|---|---|
| `Case` | id, військовий (ID), тип (поранення / травма / хвороба), дата, статус етапу, частина |
| `Event` | case_id, тип події, джерело (МІС / ЕСОЗ / СЕДО / ...), час, посилання на запис у джерелі |
| `Requirement` | який документ потрібен для цього типу кейсу, на підставі якого НПА |
| `DocumentRef` | case_id, вид документа, джерело, посилання, статус (немає / є / є помилка / завантажено вручну) |
| `Deadline` | case_id, тип правила, версія норми, підтверджена початкова подія, календарна одиниця, дата, статус |
| `Access` | хто що бачить (роль → поля) |

Медичні документи лишаються у належних джерелах; запасні завантаження потребують погодженого захищеного сховища. Метадані й посилання теж потребують підстави та захисту. Реальний контур, категорії й авторизацію / застосовний захисний маршрут погоджує власник (N09, N14–N15); прототип — лише на моках.

### Розмежування доступу (обов'язково)

- **Боєць:** належні відомості про свій кейс із погоджених джерел; доступ до медичної інформації за передбаченою процедурою.
- **Командир / служба супроводу:** необхідні адресні відомості про лікування й задачі за своїми повноваженнями; **без діагнозу і клінічних записів у цьому інтерфейсі**. Нормативна основа — N16 ст.260–262, N17 пп.3–5, N18; конкретні поля / посадові доступи погоджуються володільцем (N09, N11).
- **ВЛК:** повний медичний пакет у МІС ЗСУ.
- **Представник:** законні повноваження / належне делегування й окремий регламент доступу; споріднення не означає повний доступ. Наявність такої реалізації в Армія+ не підтверджено.

## 7. Відкриті питання (зібрати відповіді до 29.11)

1. Які саме документи / записи й права доступні погодженому оркестратору через законний цивільний канал? Нормативні рамки перевірені у фазі 3, готовність формату й API не встановлена.
2. Яке охоплення еПМК / MedEvac зараз (яка частка поранень)?
3. Як фактично реалізована включена до переліку N19 послуга направлення для військовослужбовців; хто підписує й який інтерфейс віддає подію?
4. Яка система веде виплати за поранення і чи віддає вона статус?
5. Де ІКС «Супровід» і чи робимо «Кейс» її частиною?
6. Які конкретні посадові ролі й поля для службової видимості погодить володілець на основі N16–N18, з урахуванням N09 і N11?
7. Що робити, коли поранений не може користуватись телефоном (довірена особа)?
8. Як реалізувати чинний електронний обмін і зберегти передбачені примірники / резерв? Усунення всіх паперових обов’язків — окрема зміна НПА, а не передумова будь-якого цифрового пакета.

## 8. Прототип (vibe coding, крок II)

Усе на моках, без реальних даних:

- **Екран бійця:** таймлайн кейсу, чекліст, релевантні календарні строки з підтвердженим початком, позначений запасний шлях.
- **Екран командира / супроводу:** список поранених підрозділу, де лікуються, етап, прострочені задачі частини.
- **Симулятор подій** для демо: «створено еПМК», «переведено», «видано довідку», «постанова ВЛК». Так на пітчі видно, як кейс оживає без жодних дій бійця.
