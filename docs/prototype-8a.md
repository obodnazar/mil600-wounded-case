## Що показуємо

1. **Боєць:** наступна дія / власник, статус кейсу, вигаданий заклад, timeline, технічний чекліст із відправкою / отриманням, орієнтир «дату отримання підтвердити», окремі винагорода й ОГД, короткий гайд.
2. **Командир / супровід:** серверна проєкція призначених кейсів; ролі перемикаються явно, клінічні поля / source refs не передаються. Адміністративний запит позначено резервом, дія ще недоступна.
3. **Аналітик:** шість визначень BO, невідоме [TBD], фіксований синтетичний snapshot і пояснення захисту груп. Числового агрегату / total / зрізів за частиною, закладом, географією немає; готовий BO-вимір не заявляється.
4. **Dev:** одна фіксована подія еПМК через спільний HMAC / schema / source-policy / DB gateway, повтор не множить ефект. Ключі лишаються на сервері. Інші джерельні сценарії явно відкладені до 8б.

Це **перший екран кожної панелі**, не завершені F / AC. Кнопки не імітують успішних неіснуючих дій. Seed — 30 вигаданих учасників, 3 навчальні групи, 9 умовних закладів; стадії / невідомі дати / повернення різні, фактичні прострочки не стверджуються. Минулі дати fixture лише привід перевірити стан, не підтвердження порушення строку.

| F02 / AC02 | DB-проєкція, timestamp / source / навчальна свіжість / owner / next action | Усі події маршруту, справжня для демо свіжість / відсутній сигнал, переходи D1 |
| F03 / AC03 | Версії / вимоги / докази / квитанція у схемі й read-only seed; різниця sent / received | Видача / доставка / виправлення / відкликання, manual demo-copy та перевірки, нова квитанція версії |
| F04 / AC04 | Фізичні інваріанти anchor / due; estimated / confirmed / unknown fixtures й правильний підпис | Runtime календар із граничними тестами; застосовність, підтвердження отримання, виправлення початку лікування |

**Жоден AC01–AC10 ще не оголошений повністю прийнятим.** SQL-інваріант чи seed не доводить доменний handler; відсутність чисел в аналітиці не замінює майбутнє приймання BO. Чотири календарні місяці не реалізовані як 120 днів; СЗЧ / санкцій / припинення виплат від таймера немає.

## D1 і робота за пріоритетом до 03.12

З канонічного [демо-плану](architecture/demo-plan.md) виконані локальна основа P0 для цього вузького handler і **P1 — зріз 8а**. D1.1 частково доведений gateway / первинною проєкцією, D1.2–D1.8 **ще не завершені**. Порядок після затвердження: P2 наскрізний D1 → P3 обов’язкові винятки й AC → P4 косметика / репетиція. Не починати 8б чи решту 9 до нового явного затвердження.

**Спрощуємо першими:** анімацію / графіки / фільтри → окремі складні форми джерел (типізовані fixtures) → велику бібліотеку зразків / гайдів → глибокий UI винятків (відтворюваний gateway fixture). Не відсікаємо F / AC, чотири панелі, D1, обидва фінансові види / докази виконання, джерельну правду, доступи / аудит, невідомі дати чи синтетику. Якщо обов’язковий AC не готовий — чесно неповний прототип і нове рішення команди, без оголошення готового MVP.
