# Архітектура «Кейсу поранення» — фаза 6

**2026-11-13 · логічну архітектуру затверджено, варіант А.** Основа — [F01–F10 / AC01–AC10](../05-product-concept.md), чотири панелі й [ADR 0001](adr/0001-legal-boundaries.md). Фази 7, 8а та [8б](../prototype-8b.md) затверджені: працюють синтетичний застосунок і SQLite. Стек / фізична модель — [ADR 0008](adr/0008-demo-stack-and-physical-schema.md), поведінка / окрема аналітична когорта — [ADR 0009](adr/0009-demo-workflow-and-frozen-analytics.md). Цільові канали й production-топологія не реалізовані. Нижче логічний проєкт, поточна доказова матриця — [фаза 9](../final-traceability.md).

**Уточнення аудиту 2026-11-14.** Прототип переписано зі збереженням стеку й схеми ([ADR 0010](adr/0010-prototype-rewrite.md), на затвердження разом із PR цього аудиту). Документи цього розділу описують **цільову логічну архітектуру**; що з неї реалізовано в прототипі, а що лишається цільовим, позначено в кожному документі блоком «Стан реалізації в прототипі» або «Уточнення аудиту 2026-11-14». Коротко не реалізовано: порядок подій за `source_order`, оптимістична ревізія кейсу, повтори / backoff outbox, інтервали правил із `RuleVersion`, окремий воркер вхідних подій, документний broker, запасне сховище, моніторинг.

## Рішення для команди

Назар погодив логічні межі й модель за ADR 0002–0005 ([рішення](../decisions.md)): один модульний сервер та реляційне сховище для навчального прототипу; джерельні адаптери з мінімальними подіями; окреме підтвердження людини / випадку; жодного прямого доступу командира до медичних джерел. Включення сервісу до реальної ІКС «Супровід» лишається питанням власникам, а не нашим рішенням про розгортання.

Альтернатива — змінити конкретну межу або сутність до коду. Реальні мікросервіси, брокер, стек і production-хостинг не обираємо без відповідних потреб та погоджень. Стек і фізичні міграції затверджуються у фазі 8а; безпека й пороги розкриття — у фазі 7.
