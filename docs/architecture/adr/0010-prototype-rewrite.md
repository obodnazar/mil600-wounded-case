# ADR 0010 — переписування прототипу: структура коду, контракт і виправлена поведінка

- Дата: **2026-11-14**. Статус: **реалізовано в гілці `claude/full-audit-and-prototype-rewrite`; на затвердження Назаром разом із PR цього аудиту**.
- Підстава: окреме доручення Назара від 2026-11-14 на повний незалежний аудит і переписування прототипу; знахідки [повного аудиту](../../reviews/claude-full-audit.md); прийняті F01–F10 / AC01–AC10 і ADR 0001–0009.
- Позначення джерел: «рішення команди» — уже затверджене; «інженерне рішення» — прийняте в цьому ADR і перевірене тестами; «питання команді» — свідомо не вирішене тут.

## Контекст

Прототип 8б працював і проходив 62 Node-тести та 12 браузерних, але був написаний у «стиснутому» стилі: 105 рядків коду довші за 300 символів, одна функція `applyEvent` на 19 типів подій із вбудованим SQL, одна функція команд із вбудованою матрицею ролей, увесь інтерфейс — один файл на 72 рядки. Незалежний аудит відтворив на цьому коді один критичний і кілька суттєвих дефектів саме в доменних переходах: кожне попереднє виправлення додавало умову в довгий рядок, а клас дефекту лишався.

## Рішення

### 1. Стек і схема не змінюються

TypeScript strict, React 19, Node HTTP, `node:sqlite`, Vite 8, Playwright — ті самі версії з `package-lock.json` (ADR 0008). Нових залежностей немає. Міграції `001` і `002` не змінено (їхні контрольні суми мають збігатися з наявними локальними БД); seed `seed-1` перенесено без зміни змісту — порівняння дампів свіжої БД старої й нової реалізації дає однакові рядки в усіх 31 порівняній таблиці (відрізняються лише тексти підписів BO-2 і BO-4 у двох аналітичних зрізах). Додано одну міграцію вперед — `003` (див. п. 4).

### 2. Структура коду (інженерне рішення)

| Шар | Де | Відповідальність |
|---|---|---|
| Контракт | `prototype/shared/api.ts` | Типи відповідей і запитів, спільні для сервера й браузера. Сервер віддає **коди станів**, українські підписи живуть в інтерфейсі |
| Сховище | `server/db/` | `Store` (SQL, транзакція, savepoint, аудит), міграції з checksum і відмова чужій БД, seed, одноразовий bootstrap |
| Чисті правила | `server/domain/rules.ts`, `calendar.ts` | Строк довідки, контроль лікування, переходи фінансового стану, ревізії пакета, злиття застосовності. Без SQL, HTTP і «зараз» |
| Домен | `server/domain/` | Задачі, журнал кейсу, документи, строки, свіжість, передумови дій, команди; обробники подій — по одному на тип у `domain/events/` з явною таблицею «тип події → правило» |
| Приймання | `server/ingest/gateway.ts` | Одна транзакція: nonce → дедуплікація → inbox → застосування → аудит |
| Проєкції | `server/read/` | Окремий DTO на роль: боєць, службова панель, аналітика, dev |
| HTTP | `server/http/` | Застосунок з єдиним порядком перевірок, декларативна таблиця маршрутів, сесія, валідація тіл |
| Інше | `server/simulator/`, `server/config/`, `server/workers.ts` | Фіксовані події симулятора, локальні ключі, фонові проходи |
| Інтерфейс | `ui/` | Компоненти, панелі, словники підписів, стани; технічні деталі — лише в dev-панелі |
| Тести | `server/tests/`, `security/security.test.ts`, `e2e/` | Через справжній HTTP-застосунок і пряме читання БД |

Захисне ядро фази 7 (`security/core.ts`, `protocol.ts`) збережено; його переформатовано без зміни поведінки (22 тести ядра проходять, канонічний хеш подій збігається зі старим для всіх 50 фікстур).

### 3. Єдиний порядок перевірок HTTP (інженерне рішення)

Заголовки безпеки → Host і loopback → без query → Origin → ліміт частоти → (для POST: точний Origin, cookie-сесія, CSRF) → маршрут і метод → роль → тіло → обробник → аудит. Роль перевіряється **до** розбору тіла. Невідомий шлях не розкривається анонімному запиту (401), відомий шлях з іншим методом дає 405. Відмова за лімітом має `Retry-After` і не пише рядок аудиту на кожен запит.

### 4. Міграція 003

- **CSRF-токен більше не зберігається.** Він виводиться з токена сесії (`sha256("demo-csrf\0" + token)`), якого сторінка прочитати не може (HttpOnly). У БД лишається тільки hash токена сесії. Наявні навчальні сесії анулюються.
- **`task.opened_by_event`** — яка подія журналу відкрила задачу. Таймлайн бійця показує для кожного кроку реальні задачі, їхніх власників і стан («очікується» / «виконано») або явну відсутність наступної дії. Це закриває розрив AC02, де власник і наступна дія були статичним рядком.

### 5. Виправлена поведінка

Кожен пункт має тест у `server/tests/regressions.test.ts`, `ingest.test.ts` або `workflow.test.ts`; для семи ключових виправлень перевірено, що вимкнення виправлення валить тест.

| Що | Було | Стало |
|---|---|---|
| Застосовність правила довідки | Пізніша еПМК з `unknown` або довідка про перебування з `no` мовчки стирали підтверджений строк | Підтверджене не знижується до «невідомо»; суперечність «так ↔ ні» йде на розбір |
| Підтверджений строк | Подія без потрібних фактів могла його обнулити | Скасовує лише підтверджена незастосовність |
| Подія раніше за попередника | Назавжди на розборі; повтор давав `duplicate` | Повторна доставка тієї самої події застосовує її рівно один раз, коли попередник надійшов |
| Відмова домену | 503 і відкат inbox: подія зникала безслідно | Подія лишається в inbox на розборі з причиною `unprocessable_event` |
| Постанови ВЛК | Друга позитивна постанова лишала дві відкриті дії; старе виконання закривало обидві | Чинна лише остання; попередня дія закривається; виконання, датоване до чинної постанови, не приймається |
| Запит командира | Один запит дозволяв необмежену кількість видач / направлень | Один запит — одне джерельне підтвердження |
| Квитанція отримання | Приймалася дата в майбутньому чи до поранення; раніша квитанція, що надійшла пізніше, не розглядалася | Неможлива хронологія й квитанція, що зрушила б підтверджений якір, ідуть на розбір |
| Орієнтир за внесенням еПМК | Зсувався повторним внесенням | Найраніше внесення |
| Нагадування про строк | Після відкликання виданої довідки не відновлювалося; перерахунок без зміни дати створював друге | Функція стану: видача закриває, відкликання повертає; ревізія зростає лише зі зміною результату |
| Суперечлива подія | Кожен повтор створював новий розбір | Один відкритий розбір на прийняту подію |
| `document.issued` іншого виду | Закривав задачу видачі без виданої довідки | На розбір |
| Розбори | Закривався лише невизначений випадок; решта лишали кейс у суперечності назавжди | Команда `close_review`: супровід закриває розбір після звірки з джерелом; подія лишається незастосованою, повторна доставка з тією самою причиною відкриває розбір знову |
| Ручні уточнення | Задачі від команд `clarify` і `gap` не закривалися | Команда `resolve_task` — лише для вручну створених задач |
| Дії без підстави | «Перевірити копію», «Підготувати результат звернення» записували успіх, коли нічого не було | Сервер повертає 409 з кодом передумови; ті самі передумови віддаються службовій панелі як доступність дій із причиною |

### 5а. Виправлення за незалежним фінальним рев’ю

Фінальне рев’ю (див. [звіт аудиту, розділ 8](../../reviews/claude-full-audit.md)) знайшло на першій версії переписаного коду 1 Critical і 8 Major. Інженерні рішення, прийняті при виправленні:

- **Довідку складає лише медслужба.** Глобальна політика джерел не дозволяє іншим джерелам подію «складено» для довідки про обставини травми; виправлення документа не змінює його стадії, а довідку можна виправити лише після видачі.
- **Застосовність контролю лікування** зливається за тим самим правилом, що й застосовність правила довідки.
- **Чинна постанова ВЛК — найпізніша за `occurred_at`**, а не остання за порядком надходження.
- **Невідомий фінансовий сигнал ніколи не є рішенням.**
- **Тригери задач довідки містять версію документа**, тож після відкликання маршрут починається знову.
- **Підтвердження запиту командира має надійти після запиту.** Порівнюється час першого надходження події до шлюзу, а не `occurred_at`: фіксовані навчальні події мають сталі дати в минулому, а запити подаються «зараз», тож порівняння за `occurred_at` зламало б демонстрацію.
- **Стадія кейсу не відкочується** подіями лікування.
- **Командир не бачить задач і розборів про виплати й лікування** і не закриває такі розбори — тимчасове обережне рішення до рішення команди про службову проєкцію.
- **Шлюз перехоплює лише відмови домену й помилки даних**; помилки програми відкочують транзакцію.

### 6. Контракт подій не змінюється

`security/event.schema.json` (19 типів) лишився без змін. Тому підтвердження виконання не несе посилання на конкретну постанову; прив'язка зроблена через час події. Додавання такого посилання — питання команді.

## Свідомо не змінено (питання команді)

1. **Ширша службова проєкція.** `rbac.md` і ADR 0001 дозволяють командиру / супроводу адресний мінімум (стан довідки, заклад, стан виплати). Прототип і далі дає тільки стадію, задачі, розбори, звернення, строк довідки й доступні дії; дату початку лікування з DTO прибрано. Розширення доступу потребує явного погодження.
2. **Чи має командир усі дії супроводу** (зараз так, як і в 8б).
3. **Автоматичне застосування події, що чекала попередника**, без повторної доставки джерелом.
4. **Якір за кількох квитанцій** різних версій і чи входить день отримання в п'ять днів.
5. **ОГД** змодельована спрощено: «період» пакета, «часткове виконання», той самий mock-адресат, що й для винагороди; технічні переліки не відтворюють юридичний склад пакетів.
6. **Вибір dev-ролі** будь-яким локальним користувачем без окремого прапорця.

## Альтернативи

- **Залишити структуру й виправити лише дефекти.** Відхилено: саме стиснена структура зробила переходи нечитабельними й дала рецидиви після попереднього аудиту.
- **Змінити стек** (фреймворк сервера, ORM, інша БД). Відхилено: не дає нічого для навчального прототипу, збільшує поверхню й ламає відтворюваність.
- **Видалити тестовий адаптер фази 7** (`security/server.ts`). Відкладено: він лишається окремим перевіреним адаптером; натомість додано тести тих самих властивостей проти застосунку (`server/tests/http-access.test.ts`, `ingest.test.ts`).
- **Перенести підписи на сервер.** Відхилено: сервер віддає коди, щоб правила не залежали від формулювань, а інтерфейс не дублював логіку.

## Наслідки

- Локальна БД 8б оновлюється міграцією 003 під час першого запуску; `npm run demo:reset` працює як раніше.
- Тести прив'язані до кодів станів, а не до українських фраз; тексти інтерфейсу перевіряють браузерні тести.
- Залишаються всі межі ADR 0008–0009: локальна демо-роль замість SSO, loopback HTTP, власник файлу SQLite може його змінити, підпис джерел демонстраційний; повного ASVS L2, допуску, production і реального електронного документообігу немає.
