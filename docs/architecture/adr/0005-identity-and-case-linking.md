# ADR 0005 — особа, призначення та випадок

- Дата: 2026-11-13. Статус: **прийнято, варіант А**. Назар затвердив фазу 6, логічну модель, доступи та ADR 0002–0005 2026-11-13; [рішення](../../decisions.md). Це не погодження установ / production-допуск.
- Основа: [A02–A04](../sources.md), F01 / F07 / F10, [модель](../data-model.md).

## Рішення

Внутрішній Subject має opaque ID, а підтверджені джерельні ідентифікатори відображаються через IdentityLink із namespace, доказом і строком чинності. Army ID, MIL ID, номер військового документа та `patient_id` не тотожні; конкретний законний обмін / mapping ще погоджується. Не робити РНОКПП / ПІБ загальним ключем подій чи публічних URL і не вигадувати структуру токена Армія+.

Окремо перевіряються: **та сама особа; той самий випадок; чинна область службового доступу**. Подія з відомим patient ref не доводить, що це саме попереднє поранення. Для підтвердженого incident ref у погодженому namespace — приєднання до наявного кейсу; невизначене зіставлення — ReviewItem і рішення належної ролі. Два різні випадки однієї людини не зливаються автоматично. Адміністративний кейс може очікувати медджерело, але не засвідчує його факт.

Призначення частини UnitAssignment і AccessGrant — окремі часові сутності. Довірений контекст сервера / чинний scope визначають читання; вхідний `unit_id`, роль у браузері чи минуле призначення не надають права. Зміна призначення й відкликання прав обробляються окремо від медичного маршруту.

## Альтернативи

- Зіставлення за іменем / датою народження: ризик помилки й зайвих даних; не обрано.
- Один кейс на людину: приховає повторні поранення й змішає підстави виплат; не обрано.
- Автоматично створювати новий кейс на кожну еПМК: дублікати / повтори; не обрано.

У демо всі mapping / призначення синтетичні, є сценарій невизначеного збігу. Механізм production SSO / registry API не реалізований і не підтверджений. Регламент представництва — окремий B03, не спільний пароль бійця.
