# ADR 0002 — межа сервісу й розміщення

- Дата: 2026-11-13. Статус: **запропоновано на затвердження фази 6**.
- Основа: [концепція](../../05-product-concept.md), [A05](../sources.md), [ADR 0001](0001-legal-boundaries.md).

## Рішення

Для навчального прототипу — один модульний сервер із явними модулями доступу, кейсу, інтеграцій, правил, документних посилань та агрегатів; вебклієнт, реляційна БД і фоновий воркер. Не розбивати кожну роль на мікросервіс. Стек / СУБД / ORM і хостинг обрати у фазі 8а; схему міграції не створювати до затвердження логічної моделі.

Цільова організаційна перевага — модуль у погоджених межах ІКС «Супровід», якщо власник підтвердить готовність / відповідність та відсутність дублювання. До відповіді не стверджувати фактичне розміщення; відокремлюваний модуль може бути самостійним сервісом у погодженому контурі МОУ. Функціональний контракт не залежить від цього вибору.

## Альтернативи й наслідки

- Окремий production-сервіс зараз: можна ізолювати відповідальність, але потрібні власники, регламент і додаткові операційні витрати; не обраний без підтвердження.
- Мікросервіси / брокер одразу: більше незалежного масштабування, але невиправдана складність навчального демо; відкласти до виміряної потреби.
- Статичний сайт із JSON: швидкий макет, але не виконує серверний RBAC, транзакційні події й аудит; не є прийнятною реалізацією F10 / AC10.

Це уточнює пропозицію §4 початкової концепції, а не оголошує «Супровід» відсутнім чи непридатним. Власник уточнює межі до production. Демо не деплоїти без окремого запиту.
