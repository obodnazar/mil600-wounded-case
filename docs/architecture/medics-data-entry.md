# Де медики вводять дані й як кейс їх отримує

**2026-11-13 · логічну архітектуру затверджено, варіант А; реальні обміни не погоджені.** Чинний документний порядок відділений від охоплення систем і нашого майбутнього адаптера. Джерела / дати — [A01–A10](sources.md), норми — [N04](../../regulation/primary-card-879.md), [N01](../../regulation/vlk-402.md), [N17](../../regulation/document-exchange-901.md), [N11](../../regulation/health-secrecy-2801.md). Власники не надавали внутрішніх схем або доступу. Принцип: **лікарям не створюємо ще одного застосунку**.

## Чинний ввід за етапами

| Етап / хто | Де й що оформлює зараз за відкритими джерелами | Коли / паперова частина | Статус знання |
|---|---|---|---|

ПМК пацієнту / належному представнику надається за N04 п.8; представник не отримує нового цифрового права лише через споріднення. Медик виправляє помилку **у своїй системі**, а не редагує медичний факт у «Кейсі». Адміністративний запасний ввід супроводу — тільки заявлена потреба / посилання / задача уточнення.

## Цільовий шлях до нашої БД

1. Чинний запис створюється й підписується належною роллю у джерелі. ЕПМК — можливий тригер; відсутність еПМК не блокує адміністративну ініціацію ADR А.
2. **Погоджений адаптер біля джерела** отримує лише дозволені відомості: через подію, якщо власник її надає, або погоджену вибіркову звірку API. Для СЕДО — документ / квитанція; для цивільного закладу — його законний погоджений канал, не загальне викачування ЕСОЗ.
3. Адаптер перетворює запис на мінімальний внутрішній конверт: особа як локальне посилання, випадок / епізод, подія, джерельна версія, час, вид документа й посилання. Клінічний текст, діагнози й вкладення не передаються в оркестратор. Доступ адаптера до джерела також потребує прав — мінімізація їх не створює.
4. Шлюз перевіряє джерело, право на цей вид події й схему, inbox забезпечує повтори. Зіставлення особи / випадку відділене від довіри до джерела; невпевненість дає ручний розбір, не новий медичний факт.
5. Домен зберігає метадані й доступні рольові проєкції. Пакет для ВЛК — узгоджений список належних документів, а фактична передача / доступ відбуваються в дозволеному документному каналі з квитанцією. Наш зелений індикатор не замінює таку передачу.

У прототипі цей самий вхід отримує **тільки синтетичні події dev-адаптера**. Справжніх з’єднань з МІС / ЕСОЗ / СЕДО не буде. Назви систем на кнопках — роль симуляції, не доказ сумісності API.

## Що саме означає «на основі FHIR»

Використовуємо семантику фіксованого HL7 FHIR R4 4.0.1 (A10) для узгодження понять. Внутрішній конверт **не є FHIR Bundle / ресурсом** і не називається сертифікованою реалізацією FHIR. Фактичний контракт кожного джерела реалізується адаптером після погодження; версію його профілю фіксуємо окремо.

| Ресурс FHIR / значення | Що знайдено саме в українському ЕСОЗ | Наше мінімальне відображення / межа |
|---|---|---|
| `Patient` — особа, яка отримує допомогу | A07–A08 мають `patient_id`, перевірку пацієнта та належності запису; A08 також вказує Person identifier. Це не підтвердження endpoint `/Patient` | Локальний `subject_id` через перевірений IdentityLink; без ПІБ / дати народження / РНОКПП у події. Невідомий зв’язок — ручна звірка |
| `Encounter` — взаємодія із закладом | A07: REST `/api/patients/{patient_id}/encounters/{encounter_id}`, `encounter:read` і ABAC; є зв’язок з епізодом | `source_stream`, тип надходження / переведення / виписки, дозволені дати й посилання. Не переносити весь response з діагнозами |
| `EpisodeOfCare` — період відповідальності надавача, може містити взаємодії | A08: REST `/api/patients/{patient_id}/episodes/{episode_id}`, `episode:read` і ABAC | TreatmentEpisode пов’язує джерельні епізоди з нашим випадком; переведення не створює новий відлік безперервного лікування. Епізод ЕСОЗ не дорівнює кейсу поранення |
| `DocumentReference` — метадані й посилання на документ | У переглянутих A07–A09 універсальний доступ до епікризу як DocumentReference **не підтверджений**. A09 описує інші визначені медичні висновки, не загальний епікриз | Власний DocumentRef із source system / record / version, видом і походженням; це концептуальне відображення, не обіцянка API. СЕДО може передати документ без будь-якого FHIR endpoint |

Не робимо висновок «ЕСОЗ не має DocumentReference взагалі»: перевірено перелічені відкриті методи, не повний внутрішній каталог. Не використовуємо документацію інших країн із назвою eHealth як доказ українського контракту. Для нового сервісу потрібні належні підстави та погоджені права, а не лише `scope` у документації.

## Відсутня подія й запасний шлях

| Випадок | Поведінка / відповідальний |
|---|---|
| Джерело тимчасово недоступне | Позначити актуальність, повторити лише технічну доставку за обмеженим правилом; оператор бачить код помилки без медичного вмісту |
| Немає очікуваного повідомлення | Супровід отримує задачу уточнення; адаптер виконує погоджену звірку, якщо такий API існує. Відсутність події не є відсутністю лікування |
| Є паперовий документ / непідключений заклад | Адміністративна ініціація й запит належному автору / одержувачу. Цільове фото — окрема захищена резервна копія з перевіркою повноважень і джерела; не оригінал |
| Запасний шлях у демо | Вибір підготовленого вигаданого зразка, мітка «копія, очікує перевірки», потім окрема симульована перевірка джерела. Реального upload медичних файлів немає |
| Дані / версії суперечать одне одному | ReviewItem із відповідальним, обидва джерела видимі лише належній ролі; жодного тихого виправлення медичного запису або «останній час прибуття переміг» |

Ідемпотентність, порядок, відкликання документа й транзакційні гарантії — [контракт подій](event-contract.md). Юридичну силу документа перевіряє належна процедура джерела; HMAC конверта доводить лише його технічне походження, не підпис меддокумента.
