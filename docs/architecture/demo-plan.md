# Мінімальний демо-шлях і лінія відсікання

**2026-11-13 · вимога Назара до фаз 6 і 8.** Затверджений обсяг — F01–F10 / AC01–AC10, чотири панелі. Пітч — **2026-12-03** за [завданням курсу](../00-assignment.md). Пріоритети нижче — порядок побудови й спрощення представлення, а не непомітне скасування прийнятого MVP. Одну сторінку простою мовою готуємо **у фазі 9**, зараз лише фіксуємо вимогу.

## Порядок реалізації за залежностями

| Черга | Що має з’явитися | Готовність до переходу далі |
|---|---|---|
| P0 — основа | Серверні межі ролей / scope, контракт подій, транзакційний запис / повтор, аудит і мінімальна БД; синтетичні сесії / дані | Негативні перевірки доступу та повтору проходять. Фаза 7 уточнює контролі; реальних даних немає |
| P1 — зріз для 8а | Запуск, міграція / seed, навігація та перший екран **кожної з чотирьох панелей**, банер, чернетка мінімального шляху | PR 8а зі скриншотами, матрицею «готово / ще ні» й обраним стеком → **зупинка, затвердження**. P0 не замінює обов’язковий показ усіх панелей |
| P2 — наскрізний шлях | Симулятор → той самий шлюз → стан / задача → проєкції бійця й частини → фінансове пояснення → агрегат | Шлях D1 нижче відтворюється, повтор не дублює результат, є докази отримання документа й виконання |
| P3 — обов’язкові винятки | Адміністративна ініціація без еПМК / входу бійця, невизначений збіг, пропущена подія, невідома дата, виправлення / повернення / відмова, два фінансові види, прихована група | Усі AC01–AC10 і S1–S9 перевірені; не тільки успішна демонстрація. Сценарії можуть запускатися fixtures / dev-кнопками замість складних майстрів |
| P4 — подача | Зручність першого кроку, читабельність мобільного екрана, стабільний reset демо, скриншоти й репетиція | Є сценарій показу та чесні позначки симуляцій; додаткова косметика лише після обов’язкового приймання |

Це порядок майбутньої реалізації; фазою 6 жоден пункт не реалізований. Ризик часу обговорюється на 8а з фактичною готовністю, а не з вигаданими оцінками днів чи швидкості команди.

## D1 — мінімальний показ на одному вигаданому випадку

| Крок | Хто / що показуємо | Доказ цінності / функції |
|---|---|---|
| D1.1 | Dev-панель: симульована еПМК; панель бійця оновлюється | F01 / F02 / F09: кейс, джерело, час, відповідальний; без дій бійця |
| D1.2 | Надходження / переведення; у частини задача довідки; відома й невідома початкові дати як окремі fixtures | F02 / F04: наступна дія, застосовне календарне правило, невідоме не стає датою; ніяких санкцій |
| D1.3 | Підготовку медслужбою / видачу командиром відтворено належними джерелами, потім окреме одержання адресатом | F03 / F04 / F10: походження й доставка розділені; командир не бачить клінічних полів |
| D1.4 | До завершення основної ВЛК показуємо окремий стан винагороди за лікування | F06: цей маршрут не заблокований очікуванням постанови |
| D1.5 | Належна роль направляє; demo-vlk підтверджує пакет / постанову; наступна адміністративна дія окремо | F05 / F03: технічний чекліст не вирішує медичний зміст і не є бар’єром направлення |
| D1.6 | Окрема ОГД: повернення / уточнення, рішення та підтверджене виконання; інший період може лишатися відкритим | F06: зрозумілі мотив / адресат / результат, без реальних сум або обіцянки коштів |
| D1.7 | Аналітична панель: фіксована синтетична когорта, BO-1…BO-6, невідоме / знаменник / пригнічення | F08: дані демо не є baseline, без персональних рядків. Один випадок D1 не є когортою для публікації агрегату |
| D1.8 | Окремий швидкий fixture без входу бійця: супровід продовжує задачу; повтор події й заборонений клінічний доступ | F07 / F09 / F10: допомога без нового доступу родичу, недублювання й серверна відмова |

Для BO потрібен seed погодженого розміру з фази 8, а не розмноження одного D1 для імітації ефекту. Демо має детермінований reset лише синтетичної БД й однаковий відтворюваний результат; це не операція над реальним середовищем.

## Чітка лінія відсікання

**Спрощуємо в цьому порядку, якщо часу бракує:**

1. Прибираємо анімацію, складні графіки, зайві фільтри / сортування / експорт; залишаємо зрозумілі картки й фіксовану когорту з BO-визначеннями та невідомими значеннями.
2. Замість окремого великого UI для кожного джерела / фінансового виду — один типізований dev-симулятор і параметризовані fixtures. Обидва види виплати / періоди, відмова / повернення / виконання й усі перевірки лишаються.
3. Замість великої бібліотеки документів / навчальних матеріалів — невеликий підготовлений набір вигаданих зразків та короткий гайд. Технічний checklist, резервна копія / перевірка й правильне походження зберігаються.
4. Замість глибоких екранів рідкісних сценаріїв — відтворюваний fixture через той самий серверний контракт і показаний кінцевий стан. Негативні / граничні тести не вилучаються; жодної прихованої прямої зміни БД замість шлюзу для презентації.

**Вище лінії — обов’язково лишається:** чотири панелі, D1, F01–F10 / AC01–AC10, належні ролі / scope / серверні відмови, аудит, підпис / схема вхідної події, повтор і конфлікт, відсутня дата без вигаданого таймера, обидва фінансові маршрути й підтвердження виконання, синтетика / банер, агрегати без розкриття груп. Структуру й приймання не міняємо косметичним скороченням.

**Нижче лінії — не починаємо:** B01–B06, справжні інтеграції / OCR / нове представництво / SMS / повний офлайн, мікросервіси, production-деплой, кастомна BI-платформа. Ці пункти вже поза затвердженим MVP, не резервні задачі «паралельно».

Якщо навіть після цих спрощень не проходить обов’язковий AC, **MVP не оголошується завершеним**. На контрольній точці 8а / 8б команда бачить конкретний список готового / невиконаного й обирає: довести потрібний AC або явно погодити зменшений демонстраційний обсяг із відомими обмеженнями. Такий показ позначається неповним прототипом, а не повністю прийнятим MVP; нове рішення записується. Безпеку, правові межі й синтетичність не відсікаємо заради дати.
