## Мінімальний конверт

| Поле | Контракт / перевірка |
|---|---|
| `schema_version`, `event_id`, `event_type` | Версія контракту; стабільний ID на всі повтори цього повідомлення; дозволений тип із реєстру нижче. Зміна смислу потребує нової версії |
| `source_system`, `source_record_ref`, `source_stream`, `source_version`, `source_order` | Довірене джерело з налаштувань ключа, локальний opaque ref, потік однієї джерельної сутності, token ревізії та необов’язковий підтверджений порядковий номер джерела. Невідомий порядок не підміняється часом отримання. У прототипі `source_order` зберігається, але не використовується: порядок версій потоку задає необов’язкове поле конверта `supersedes_version` — явне посилання на попередню ревізію (аудит 2026-11-14) |
| `subject_ref`, `incident_ref`, `episode_ref` | Локальні посилання. `incident_ref` / `episode_ref` можуть бути null; непідтверджений зв’язок не означає автоматичного створення / злиття кейсу. Клінічні дані для пошуку особи не передаються |
| `occurred_at`, `recorded_at` | Час події в джерелі та час запису джерелом, часовий пояс / UTC. Наш `received_at` ставиться сервером окремо. Невідома дата юридичного відліку не виводиться з цих технічних часів |
| `payload` | Строгий allowlist за типом: дозволені дати / коди / refs / вид виплати й період. Немає довільного клінічного тексту, діагнозів, base64, токенів чи довільного URL; додаткові поля на вході оркестратора відхиляються без збереження сирого body |

Підпис / key ID / timestamp / nonce — у транспортному заголовку, а не в `payload`. Пропозиція для демо: HMAC перевіряється над сирими байтами разом із timestamp та nonce, ключ визначає джерело й дозволені event types. Точний протокол / replay-window та валідація — фаза 7; секрет лише на сервері. Повтор дозволяється з новими транспортними timestamp / nonce, але тим самим `event_id` і незмінним семантичним вмістом. HMAC не замінює КЕП документа.

```json
{
  "schema_version": "case-event/1",
  "event_id": "demo-event-epmk-1",
  "event_type": "medical.primary_recorded",
  "source_system": "demo-mis",
  "source_record_ref": "demo-primary-1",
  "source_stream": "demo-primary-1",
  "source_version": "v1",
  "source_order": 1,
  "subject_ref": "demo-subject-1",
  "incident_ref": "demo-incident-1",
  "episode_ref": null,
  "occurred_at": "2026-11-13T08:00:00Z",
  "recorded_at": "2026-11-13T08:01:00Z",
  "payload": {"document_kind": "primary_medical_card", "document_version": "1"}
}
```

Усі ID й час прикладу синтетичні; це не дата реального випадку. Повний набір полів кожного типу й машинні схеми реалізуються перед прийманням подій у прототипі; фазою 6 код валідації не створюється. (Історичний стан фази 6; машинні схеми реалізовано — див. вище.)

|---|---|---|

| `source.sync_gap` | Медджерело повідомляє, що очікуваний сигнал (тип і потік) не надійшов | Доводити відсутність лікування чи СЗЧ; закривати прогалину чужим сигналом |

`case.open`, `task.request_clarification`, `certificate.request_issue`, `referral.request_issue`, `support.register_request` — **користувацькі команди**, не медичні / фінансові події. Доступ перевіряє сервер за [RBAC](rbac.md). Командир може ініціювати дію своєї компетенції; її юридичний документ лишається у джерелі. Демо-адаптер може повернути явно симульоване підтвердження СЕДО, але це інший запис із джерелом та автором команди. Супровід не має командного права підпису.

**Уточнення аудиту 2026-11-14.** Назви вище — логічні. У прототипі всі команди надсилаються на `POST /api/commands` полем `action`: `admin_open`, `clarify`, `issue_certificate`, `refer_vlk`, `support_request` (відповідають п’яти логічним), а також `gap`, `resolve_support`, `copy`, `verify_copy`, `resolve_review`, `close_review` (закрити розбір після звірки з джерелом; подія лишається незастосованою) і `resolve_task` (закрити вручну створене уточнення чи позначку прогалини). Передумови дії перевіряє сервер і відповідає 409 з кодом причини; ті самі передумови службова панель отримує як доступність дій. Типи запитів і відповідей — [shared/api.ts](../../prototype/shared/api.ts), опис — [README прототипу](../../prototype/README.md).

Зміни IdentityLink / UnitAssignment / AccessGrant не приймаються як довільні поля медичних подій. Для production це окремий довірений контракт і посадова процедура власника; їх ще не отримано. У демо початкові призначення задає серверний seed, а відкликання / передача scope відтворюються контрольованими fixtures з аудитом. Звичайний користувач або `demo-mis` не може створити собі грант через шлюз. **Уточнення аудиту 2026-11-14:** fixtures для відкликання гранта чи передачі scope у прототипі немає — не реалізовано; тести відтворюють відкликання прямою зміною seed-таблиць.

## Доставка, порядок і помилки

1. **Приймання:** автентифікація джерела → право на тип / scope → перевірка схеми → перевірка повтору → запис мінімального inbox. Повертаємо приймання тільки після його стійкого запису; це не статус виконання доменної дії.
2. **Ідемпотентність:** unique `(source_system, event_id)`. Той самий ID з іншим семантичним digest — конфлікт, не оновлення. Додатковий unique `(source_system, source_stream, source_version, event_type)` захищає від нового ID для тієї самої ревізії; відмінний digest тут теж конфлікт. Digest рахується з узгодженої канонічної семантичної частини, без транспортних nonce / timestamp / нашого received_at. Метод канонізації фіксується в реалізації контракту.
3. **Порядок:** порівнюємо `source_order` лише всередині одного source stream, якщо джерело дає підтверджений порядок. `source_version` визначає рівність ревізії, не її старшинство. Opaque revision / ETag не сортуємо як число; локальний лічильник прибуття адаптера теж не є джерельним порядком. Старіша подія лишається в історії, не повертає поточний стан назад; прогалина версій або невідомий порядок — reconciliation / ReviewItem. Різні джерела не мають спільного лічильника: конфлікт вирішує правило авторитетності / людина, не `received_at`.
4. **Транзакція:** lock / optimistic revision кейсу; InboxEvent → CaseEvent → поточний стан / задача / правило / аудит → Outbox атомарно. Повтор після збою не створює другу задачу. Вихідний одержувач також має ключ ідемпотентності; exactly-once між установами не обіцяємо.
5. **Відкликання / виправлення:** нова версія / компенсуюча подія посилається на стару. Доставку й технічну комплектність попередньої версії не переносимо на нову без підтвердження. Перерахунок календаря має новий доказ, версію норми й аудит; історію не стираємо.
6. **Повтор:** технічні timeout / тимчасова помилка → обмежений backoff із лімітом, далі оператор / ручний розбір. Відмова в правах, некоректний підпис, семантичний конфлікт або невідома особа не повторюються нескінченно як технічний збій. Ліміти [TBD] у фазі 7.
7. **Тиша джерела:** freshness marker і задача відповідальному; звірка за погодженим watermark / cursor з перекриттям вікна, якщо власник надає такий метод. Не вигадуємо endpoints / частоту, не скануємо всю ЕСОЗ. Немає каналу — чинний адміністративний запасний шлях.

## Команди й читання

Пропоновані API нашого прототипу: `GET /api/cases/:id` — рольова проєкція; `POST /api/cases` — адміністративна ініціація; `POST /api/cases/:id/commands` — типізована команда; `POST /api/integration/events` — окремий джерельний вхід; `GET /api/analytics` — тільки фіксовані агрегати; `POST /api/demo/events` — dev-сесія → серверний адаптер → інтеграційний шлюз. Це наші назви, не існуючі URL установ.

**Уточнення аудиту 2026-11-14.** Фактичні endpoint-и прототипу: `GET /api/session`, `POST /api/demo/session` (навчальний вибір ролі), `GET /api/patient`, `GET /api/staff`, `GET /api/cases/:id`, `GET /api/cases/:id/clinical-document`, `GET /api/analytics`, `GET /api/dev`, `GET /api/guide` (без сесії), `POST /api/commands` (усі команди, зокрема адміністративна ініціація `admin_open`; `case_id` — у тілі), `POST /api/integration/events`, `POST /api/demo/events`, `POST /api/demo/analytics` (вибір одного з двох зафіксованих зрізів), `POST /api/demo/primary` (сумісність із 8а). Окремих `POST /api/cases` і `POST /api/cases/:id/commands` немає. Порядок перевірок єдиний: локальність → Origin → ліміт частоти → сесія і CSRF → роль → тіло.

Команди мають `(actor, route, idempotency_key, request_digest)`; інший body з тим самим ключем відхиляється. Перед повторною відповіддю з кешу заново перевіряються поточні права: відкликаний доступ не відновлюється кешем. Немає підтвердження сервера — UI не показує успіх. Невідомий ресурс / відсутній scope не розкривають чужі записи; точні HTTP-відповіді й негативні тести визначені в RBAC, не фактично пройдені. (Історичний стан фази 6; на 2026-11-14 їх перевіряють тести застосунку — [http-access.test.ts](../../prototype/server/tests/http-access.test.ts).) У прототипі ключ команди — `(actor, id, digest)` без окремого `route`.

## Стан реалізації в прототипі (аудит 2026-11-14)

Нумерація — як у розділі «Доставка, порядок і помилки». Цільові формулювання вище не змінено; тут — що з них фактично є в локальному застосунку. Докази — тести [ingest.test.ts](../../prototype/server/tests/ingest.test.ts) і [regressions.test.ts](../../prototype/server/tests/regressions.test.ts).

| Пункт | У прототипі | Статус |
|---|---|---|
| 1. Приймання | Підпис → схема → політика джерела, далі в одній транзакції: nonce → дедуплікація → inbox → застосування → аудит. 202 лише після запису. Відмова домену, зокрема порушення обмеження БД, не дає 5xx: подія лишається в inbox зі станом `pending_review` і причиною розбору | Реалізовано |
| 2. Ідемпотентність | Два унікальні ключі, канонічний digest без `event_id` і транспортних полів; той самий ключ з іншим змістом → 409 і один відкритий розбір на прийняту подію, скільки б разів суперечливу версію не надсилали | Реалізовано |
| 3. Порядок | `source_order` не використовується. Нова версія потоку має збігатися з останньою прийнятою або явно посилатися на неї (`supersedes_version`); інакше розбір. Подія, що прийшла раніше за попередника, застосовується рівно один раз під час повторної доставки джерелом. Автоматичного повторного застосування без нової доставки немає. Між різними потоками чинність (наприклад, остання постанова ВЛК) визначається останньою прийнятою подією та часом події | Частково; автоматичне застосування й авторитетність між потоками — [питання команді, аудит 2026-11-14] |
| 4. Транзакція | Одна `BEGIN IMMEDIATE` транзакція SQLite з вкладеною межею для домену; збій аудиту відкочує все. Оптимістичної ревізії кейсу немає: `wound_case.revision` лише зростає й не перевіряється (один процес, один writer) | Атомарність реалізовано; lock / optimistic revision — не реалізовано в прототипі, цільова архітектура |
| 5. Відкликання / виправлення | Виправлення вимагає чинної попередньої версії; квитанція не переноситься на нову версію. `CaseEvent.supersedes_id` не заповнюється. Рядок строку оновлюється на місці; `calculation_revision` зростає лише за зміни результату, попереднє нагадування закривається як застаріле | Частково |
| 6. Повтор | Вхідна обробка синхронна; повторів і backoff немає. Outbox лише локально підтверджується воркером: `next_attempt_at` не використовується, шляху помилки доставки немає | Не реалізовано в прототипі; цільова архітектура |
| 7. Тиша джерела | Лише явна подія `source.sync_gap` від джерела або ручна позначка супроводу (`gap`), яку можна закрити вручну (`resolve_task`). Виявлення тиші за часом і звірки за watermark / cursor немає | Частково |
| Розбори | Невизначений випадок закриває явна звірка (`resolve_review`). Інші причини службова роль закриває після звірки з джерелом (`close_review`): подія лишається незастосованою, повторна доставка з тією самою причиною відкриває розбір знову | Реалізовано; хто має закривати розбори в цільовому процесі — [питання команді, аудит 2026-11-14] |
