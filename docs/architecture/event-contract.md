# Контракт подій і команд

**2026-11-13 · пропозиція власного контракту `case-event/1`.** Це не фактичний API ЕСОЗ / МІС ЗСУ. Базова семантика й межі FHIR — [ввід медиками](medics-data-entry.md); альтернативи доставки — [ADR 0003](adr/0003-events-and-reconciliation.md). Числові ліміти / таймаути затверджуються у фазі 7, не заявлені як нормативні.

## Мінімальний конверт

| Поле | Контракт / перевірка |
|---|---|
| `schema_version`, `event_id`, `event_type` | Версія контракту; стабільний ID на всі повтори цього повідомлення; дозволений тип із реєстру нижче. Зміна смислу потребує нової версії |
| `source_system`, `source_record_ref`, `source_stream`, `source_version`, `source_order` | Довірене джерело з налаштувань ключа, локальний opaque ref, потік однієї джерельної сутності, token ревізії та необов’язковий підтверджений порядковий номер джерела. Невідомий порядок не підміняється часом отримання |
| `subject_ref`, `incident_ref`, `episode_ref` | Локальні посилання. `incident_ref` / `episode_ref` можуть бути null; непідтверджений зв’язок не означає автоматичного створення / злиття кейсу. Клінічні дані для пошуку особи не передаються |
| `occurred_at`, `recorded_at` | Час події в джерелі та час запису джерелом, часовий пояс / UTC. Наш `received_at` ставиться сервером окремо. Невідома дата юридичного відліку не виводиться з цих технічних часів |
| `payload` | Строгий allowlist за типом: дозволені дати / коди / refs / вид виплати й період. Немає довільного клінічного тексту, діагнозів, base64, токенів чи довільного URL; додаткові поля на вході оркестратора відхиляються без збереження сирого body |

Підпис / key ID / timestamp / nonce — у транспортному заголовку, а не в `payload`. Пропозиція для демо: HMAC перевіряється над сирими байтами разом із timestamp та nonce, ключ визначає джерело й дозволені event types. Точний протокол / replay-window та валідація — фаза 7; секрет лише на сервері. Повтор дозволяється з новими транспортними timestamp / nonce, але тим самим `event_id` і незмінним семантичним вмістом. HMAC не замінює КЕП документа.

Вигаданий приклад (власний конверт, не FHIR-ресурс):

```json
{
  "schema_version": "case-event/1",
  "event_id": "demo-event-epmk-1",
  "event_type": "medical.primary_recorded",
  "source_system": "demo-mis",
  "source_record_ref": "demo-primary-1",
  "source_stream": "demo-primary-1",
  "source_version": "v1",
  "source_order": 1,
  "subject_ref": "demo-subject-1",
  "incident_ref": "demo-incident-1",
  "episode_ref": null,
  "occurred_at": "2026-11-13T08:00:00Z",
  "recorded_at": "2026-11-13T08:01:00Z",
  "payload": {"document_kind": "primary_medical_card", "document_version": "1"}
}
```

Усі ID й час прикладу синтетичні; це не дата реального випадку. Повний набір полів кожного типу й машинні схеми реалізуються перед прийманням подій у прототипі; фазою 6 код валідації не створюється.

| Група дозволених типів | Джерело / мінімальна семантика | Чого подія не дозволяє |
|---|---|---|
| `medical.primary_recorded` | Погоджене медджерело; №001/о / версія, перевірений зв’язок особи / випадку | Командиру створити еПМК або автоототожнити різні поранення |
| `care.admitted`, `care.transferred`, `care.discharged`, `care.start_confirmed` | Медджерело / належний адресний канал; епізод, дозволені заклади / дати. `care.start_confirmed` окремо засвідчує початок для правила | Доводити СЗЧ чи починати відлік із першого повідомлення, яке прийшло в мережі |
| `document.prepared`, `document.issued`, `document.received`, `document.corrected`, `document.withdrawn` | Визначене джерело / одержувач, ref і версія документа, роль події, квитанція / ref заміни. Для received обов’язкові `recipient_ref`, `recipient_kind`, підтверджена дата й доказ; `servicemember` відрізняється від part / vlk | Вважати копію оригіналом, стару квитанцію доказом одержання нової версії або довільну доставку початком строку N16 ст.260 |
| `referral.issued`, `vlk.package_received`, `vlk.package_returned`, `vlk.decision_recorded`, `service.action_confirmed` | Належний видавець / ВЛК / виконавець; ref, службовий дозволений код, версія. Для пакетів — route / packet_ref / packet_revision / адресат / підтверджена дата; повернення має код мотиву | Генерувати медичний висновок чеклістом або закривати всі подальші дії однією постановою |
| `finance.package_received`, `finance.status_recorded` | Визначене фінджерело, вид `reward` / `ogd`, період, код стану / мотиву, ref рішення / виконання; для пакета ОГД — packet_ref / packet_revision / конкретний адресат / дата. Повернення пов’язане з тим самим logical packet, а не новим випадком | Обчислювати право чи суму; вважати призначення фактичним зарахуванням без відповідного джерела |

`case.open`, `task.request_clarification`, `certificate.request_issue`, `referral.request_issue`, `support.register_request` — **користувацькі команди**, не медичні / фінансові події. Доступ перевіряє сервер за [RBAC](rbac.md). Командир може ініціювати дію своєї компетенції; її юридичний документ лишається у джерелі. Демо-адаптер може повернути явно симульоване підтвердження СЕДО, але це інший запис із джерелом та автором команди. Супровід не має командного права підпису.

Зміни IdentityLink / UnitAssignment / AccessGrant не приймаються як довільні поля медичних подій. Для production це окремий довірений контракт і посадова процедура власника; їх ще не отримано. У демо початкові призначення задає серверний seed, а відкликання / передача scope відтворюються контрольованими fixtures з аудитом. Звичайний користувач або `demo-mis` не може створити собі грант через шлюз.

## Доставка, порядок і помилки

1. **Приймання:** автентифікація джерела → право на тип / scope → перевірка схеми → перевірка повтору → запис мінімального inbox. Повертаємо приймання тільки після його стійкого запису; це не статус виконання доменної дії.
2. **Ідемпотентність:** unique `(source_system, event_id)`. Той самий ID з іншим семантичним digest — конфлікт, не оновлення. Додатковий unique `(source_system, source_stream, source_version, event_type)` захищає від нового ID для тієї самої ревізії; відмінний digest тут теж конфлікт. Digest рахується з узгодженої канонічної семантичної частини, без транспортних nonce / timestamp / нашого received_at. Метод канонізації фіксується в реалізації контракту.
3. **Порядок:** порівнюємо `source_order` лише всередині одного source stream, якщо джерело дає підтверджений порядок. `source_version` визначає рівність ревізії, не її старшинство. Opaque revision / ETag не сортуємо як число; локальний лічильник прибуття адаптера теж не є джерельним порядком. Старіша подія лишається в історії, не повертає поточний стан назад; прогалина версій або невідомий порядок — reconciliation / ReviewItem. Різні джерела не мають спільного лічильника: конфлікт вирішує правило авторитетності / людина, не `received_at`.
4. **Транзакція:** lock / optimistic revision кейсу; InboxEvent → CaseEvent → поточний стан / задача / правило / аудит → Outbox атомарно. Повтор після збою не створює другу задачу. Вихідний одержувач також має ключ ідемпотентності; exactly-once між установами не обіцяємо.
5. **Відкликання / виправлення:** нова версія / компенсуюча подія посилається на стару. Доставку й технічну комплектність попередньої версії не переносимо на нову без підтвердження. Перерахунок календаря має новий доказ, версію норми й аудит; історію не стираємо.
6. **Повтор:** технічні timeout / тимчасова помилка → обмежений backoff із лімітом, далі оператор / ручний розбір. Відмова в правах, некоректний підпис, семантичний конфлікт або невідома особа не повторюються нескінченно як технічний збій. Ліміти [TBD] у фазі 7.
7. **Тиша джерела:** freshness marker і задача відповідальному; звірка за погодженим watermark / cursor з перекриттям вікна, якщо власник надає такий метод. Не вигадуємо endpoints / частоту, не скануємо всю ЕСОЗ. Немає каналу — чинний адміністративний запасний шлях.

## Команди й читання

Пропоновані API нашого прототипу: `GET /api/cases/:id` — рольова проєкція; `POST /api/cases` — адміністративна ініціація; `POST /api/cases/:id/commands` — типізована команда; `POST /api/integration/events` — окремий джерельний вхід; `GET /api/analytics` — тільки фіксовані агрегати; `POST /api/demo/events` — dev-сесія → серверний адаптер → інтеграційний шлюз. Це наші назви, не існуючі URL установ.

Команди мають `(actor, route, idempotency_key, request_digest)`; інший body з тим самим ключем відхиляється. Перед повторною відповіддю з кешу заново перевіряються поточні права: відкликаний доступ не відновлюється кешем. Немає підтвердження сервера — UI не показує успіх. Невідомий ресурс / відсутній scope не розкривають чужі записи; точні HTTP-відповіді й негативні тести визначені в RBAC, не фактично пройдені.
